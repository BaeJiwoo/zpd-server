# 작업 진행 기록

## 2026-09-16 최신 — 상수·자료형·모듈과 명칭 정리

- `Define.hpp`를 ConnectionKey / NetworkIo / NetworkSettings로, PacketCode를 MessageCode / ErrorCode로 분리했습니다. ProtocolLimits, ServerLimits, ClientSettings에서 관련 상수와 설정을 관리합니다.
- 연결 슬롯(clientId → slotIndex), 소켓 객체(ClientInfo → ClientConnection), 방(GameSession → RoomSession), 개발용 입장 전 상태(Connected → AwaitingEntry), 송신 자료형(Delivery → OutboundPacket)의 이름을 정리했습니다.
- PacketHandler는 수신 조립·큐·로직 스레드·전송을 담당합니다. 게임 상태와 요청 처리는 GameWorld로 옮겼고 RoomRequests와 ChatRequests로 기능을 분리했습니다. 수신 함수는 ReceiveBytes, 시작 함수는 Start로 명시했습니다.
- 클라이언트를 tests/echo_client.cpp에서 client/로 옮겨 실행/자원 수명, 콘솔 입력, 명령 처리, 응답·알림 처리, 대기 요청 자료형을 분리했습니다. 전용 `zpd-client.exe`를 추가하고 기존 대화형 테스트 실행 경로도 유지했습니다.
- Protobuf 파일을 echo/session/room/chat으로 분리했습니다. 메시지 이름, 코드, 필드 번호, 헤더 바이트와 오류 동작은 유지했습니다.
- CMake는 서버·클라이언트 구현을 각 라이브러리로 한 번 컴파일합니다. VS Code 실행/디버그 설정과 최신 문서 참조도 갱신했습니다. 상세 구조는 [코드 구조](코드_구조.md)에 있습니다.
- 검증 폴더: `out/build/refactor-debug`. 기존 실행 중인 서버·클라이언트를 종료하거나 덮어쓰지 않았습니다.
- Debug 구성·최종 빌드 성공. CTest 서버 통합 테스트 1/1 통과(0.68초). `tests/chat_client_tests.py`를 전용 zpd-client 및 기존 zpd-server-tests 두 경로로 각각 실행하여 모두 통과했습니다. 양방향 UTF-8 채팅, 방 목록, 입력 대기 중 알림, 정상/원격 종료, 잘못된 응답과 미완료 요청 정리를 확인했습니다.
- Release·실제 콘솔 IME 수동 테스트는 이번에 실행하지 않았습니다. 커밋·푸시는 하지 않았습니다.

아래 기록은 당시 파일명과 빌드 위치를 포함한 이력입니다. 최신 구조와 실행 파일은 위 내용 및 코드 구조 문서를 따릅니다.

- 오류 18/19와 방 미소속 오류에 다음 입력 명령을 안내합니다. 콘솔 입력은 Unicode 이벤트에서 UTF-8로 변환하고 출력을 UTF-8로 설정합니다.

- 기본 Debug 빌드는 기존 실행 중인 서버 파일 잠금(LNK1168)으로 교체하지 못했습니다. 기존 프로세스를 종료하지 않고 MSBuild OutDir를 지정해 `out/build/windows-x64/Debug-chat`에 새 실행 파일과 필요한 DLL을 배치했습니다.

### 코드 리뷰 결과

- 게임 상태는 로직 스레드 하나만 변경하며 Stop은 해당 스레드 join 후 map과 ID 카운터를 초기화합니다.

- 8바이트 헤더가 이미 소스에 있었으나 테스트는 4바이트였던 불일치를 수정했습니다. 최대 본문은 4088바이트입니다.

## 2026-09-15 최신 상태 — 6단계 코드 분리 적용

- 사용자가 5단계 기본 동작이 정상임을 확인했습니다. 세부 통합 시나리오 전체 통과를 뜻하지는 않습니다.
- 6단계 중 Echo/Ping/Enter 요청·응답 코드 분리를 적용했습니다(06-02 일부, 06-06, 06-07 관련).
- `RequestCode`는 `MessageCode`, 패킷의 `request` 필드는 `code`로 변경했습니다.
- 헤더는 길이 2바이트(big-endian), 메시지 코드 1바이트, 오류 코드 1바이트로 총 4바이트입니다. 최대 패킷/본문은 4096/4092바이트이며 requestId는 아직 없습니다.

| 기능 | 요청 코드 / 본문 | 응답 코드 / 성공 본문 |
|---|---|---|
| Echo | 0x01 / EchoRequest | 0x81 / EchoResponse |
| Ping | 0x02 / 빈 본문 | 0x82 / 빈 본문 |
| Enter | 0x03 / EnterRequest | 0x83 / EnterResponse |
| 알 수 없는 코드 또는 응답 코드를 요청으로 수신 | 허용된 요청 이외의 코드 | 0xff / 빈 본문, UnknownRequest |

- 알려진 요청의 오류도 해당 응답 코드로 반환하며 본문은 비웁니다.
- 서버 Dispatch 및 응답 생성, 클라이언트 응답 검사, 통합 테스트를 함께 수정했습니다. 기존 Protobuf 메시지는 그대로 사용합니다.
- 테스트에는 Ping의 실제 바이트 규격, 응답 코드의 요청 사용 거절, 입장 및 중복 입장 응답 검사를 반영했습니다.
- 서버와 클라이언트는 함께 다시 빌드해야 합니다. 이전 응답 코드 규격과 호환되지 않습니다.
- Debug 빌드를 시도했으나 MSB4184(샌드박스의 Windows SDK 경로 접근 거부)로 중단됐습니다. 외부 실행 승인이 거절되어 재시도하지 않았으며, 이번 변경의 빌드 성공 및 테스트 실행은 미확인입니다.

- 현재 소스 기본 포트는 사용자가 변경한 20000입니다.

|---|---|---|

| 세션 조회 | `LogicWorker()`의 `sessions` | `ConnectionKey → PlayerSession` |

| 요청 분기 | `include/PacketHandler.hpp`의 `Dispatch()` | 패킷·원본 세션·ID 카운터·ID map을 입장 처리에 전달 |

| 입장 메시지 | `proto/echo.proto` | 빈 EnterRequest, player_id를 가진 EnterResponse |
| 대화형 클라이언트 | `tests/echo_client.cpp` | `/enter`, 임시 ID 출력, 중복 입장 안내, 응답 파싱·ID 0 검사 |

`sessions`와 `connectionsByPlayerId`는 `LogicWorker()`의 while문 밖에 있는 지역 변수입니다. 로직 스레드만 접근하므로 세션 변경에 큐 mutex를 추가하지 않습니다. 로직 스레드가 끝나면 두 map도 소멸합니다.

`m_liveConnections`는 다른 용도입니다. 네트워크 콜백과 로직 스레드가 공유하며 `m_mutex`로 보호합니다. 연결 종료 여부 확인과 종료 이벤트용 큐 공간 예약에 사용합니다.

## 한 연결의 동작 순서

1. 접속하면 Connected 이벤트가 큐에 들어갑니다.
2. 로직 스레드가 세션을 만듭니다. `playerId = 0`, `state = Connected`, `roomId`는 비어 있습니다.
3. 클라이언트가 `/enter`를 입력하면 EnterRequest를 전송합니다.
4. 로직 스레드가 세션과 현재 연결 키를 확인하고 EnterSession을 호출합니다.
5. 정상 입장이면 EnterResponse 본문을 만들고 ID 매핑을 등록합니다. 세션 ID를 설정하고 Lobby로 바꿉니다.
6. 클라이언트가 성공 응답의 임시 플레이어 ID를 출력합니다.
7. 같은 연결의 `/enter` 재요청은 AlreadyEntered 오류로 끝납니다.
8. 연결이 종료되면 Disconnected 이벤트에서 두 map의 해당 항목을 제거합니다.

세션 상태 변경은 응답 본문 생성 후, 실제 송신 완료 전에 일어납니다. 송신 실패 시 서버의 콜백이 연결 종료를 요청합니다.

## 현재 통신 규격 — 6단계 규격과 혼동하지 않기

| 필드 | 현재 크기·값 |
|---|---|
| 전체 패킷 길이 | 2바이트, 헤더 포함, big-endian |
| 요청 코드 | 1바이트; 요청과 응답이 같은 값을 사용 |
| 오류 코드 | 1바이트 |
| 헤더 합계 | 4바이트 |
| 최대 전체 / 본문 크기 | 4096 / 4092바이트 |
| 요청 식별자 | 아직 없음 |

| 요청 코드 | 값 | 요청 본문 → 성공 응답 본문 |
|---|---|---|
| Echo | `0x01` | EchoRequest → EchoResponse |
| Ping | `0x02` | 빈 본문 → 빈 본문 |
| Enter | `0x03` | EnterRequest → EnterResponse |

현재 오류 값: None=`0x00`, UnknownRequest=`0x01`, InvalidPayload=`0x02`, InvalidRequestStatus=`0x03`, AlreadyEntered=`0x11`, UnknownError=`0x99`.

`UnknownError`는 이전 `0x10`에서 변경됐습니다. 다른 버전의 클라이언트와 혼용할 때 같은 규격인지 확인해야 합니다. 6단계의 MessageCode 분리나 응답 코드 `0x81` 등은 아직 적용되지 않았습니다.

## 아직 구현하거나 검증하지 않은 부분

- `roomId`는 빈 값을 보관하는 필드까지만 있습니다. 방 생성·참가·퇴장, InRoom 상태는 후속 단계입니다.
- ID map의 등록·삭제는 구현했습니다. 특정 플레이어에게 보내기 위한 조회 함수와 실제 사용 경로는 후속 기능에서 연결합니다.
- ID 카운터는 서버 실행마다 1부터 시작합니다. 영구 계정 ID나 재시작을 넘어 유지하는 인증 정보가 아닙니다.
- 입장 전에도 Echo와 Ping은 허용됩니다. 방 요청은 아직 없으며, 추가할 때 세션 상태 검사를 함께 구현해야 합니다.
- 연결 유효성 검사 이후 시작한 처리를 중간에 취소하는 구조는 아닙니다. 검사 시 이미 종료된 대기 패킷은 버리고, 실제 송신 시에도 연결 세대를 검사합니다.
- 독립적인 PlayerManager 클래스는 만들지 않았습니다. 현재 두 map이 로직 스레드 안에서 관리 역할을 합니다.

## 재개할 때의 첫 작업 — 아직 실행하지 않음

6단계에서는 먼저 Echo·Ping·Enter의 요청 코드와 응답 코드를 분리합니다. 메시지 코드 표를 정한 뒤 `PacketCode.hpp`, `Packet.hpp`, 서버 Dispatch/응답 생성, 클라이언트 응답 검사, raw 패킷을 사용하는 테스트 코드를 함께 전환합니다.

그다음 요청 식별자와 헤더 크기를 정하고, 방 메시지 및 서버 알림 규격을 정의합니다. 오늘은 이 작업을 시작하지 않습니다. 구체적인 기준은 [6단계 작업표](MO_서버_단계별_개발_요구사항.md#6단계-요청-응답-알림-규격-정의)를 따릅니다.

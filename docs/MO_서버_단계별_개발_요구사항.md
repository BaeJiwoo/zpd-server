# MO 서버 단계별 작업표

최종 정리: 2026-09-13 · **5단계 핵심 구현 후 중단 / 6단계 미착수**

[작업 안내](README.md) · [현재 진행 기록](작업_진행_기록.md) · [코드 스타일](코드_스타일.md)

## 읽는 방법

이 문서는 앞으로 구현할 범위와 완료 기준입니다. 현재 코드 상태와 실행 기록은 별도의 진행 기록에서 확인합니다. 요구사항 번호는 이전 문서와 동일하게 유지했습니다.

1. 해당 단계의 목표와 수정 대상을 읽습니다.
2. 작업표를 위에서부터 한 항목씩 구현합니다.
3. 코드 리뷰 결과와 실제 실행 결과를 구분해 진행 기록에 남깁니다.
4. 빌드·테스트는 별도 요청이 있을 때 실행합니다. 완료 기준에 적힌 시나리오는 자동으로 실행됐다는 뜻이 아닙니다.

현재 코드의 흐름은 `연결/수신/종료 콜백 → 이벤트 큐 → LogicWorker → 세션 처리 → 응답 송신`입니다. 초기에 사용했던 3단계의 임시 요청 목록은 4단계 이벤트 큐로 대체됐습니다. 3단계만의 중간 구조를 다시 만들지 않습니다.

## 전체 순서

| 단계 | 작업 | 현재 위치 |
|---|---|---|

| 6 | 요청·응답·알림 규격 | 미착수, 재개 요청 전까지 보류 |

## 구현 범위

Windows C++20 IOCP 서버와 Protobuf를 사용합니다. 하나의 로직 스레드가 여러 플레이어와 방의 상태를 변경합니다. 최종 목표는 두 클라이언트가 같은 방에 들어가 서로의 입장·퇴장 알림을 받는 것입니다.

실제 계정 인증, 재접속 복구, 이동·전투, 데이터베이스, 서버 간 분산 처리는 이번 10단계 범위에 포함하지 않습니다.

## 1단계 Protobuf Echo 통신 완성

### 목표

서버와 클라이언트가 동일한 Protobuf 규격으로 원문 데이터를 주고받는다.

### 열어볼 파일과 수정 범위

tests/echo_client.cpp, tests/server_tests.cpp. 기존 proto/echo.proto와 PacketHandler의 Echo 처리를 사용한다.

### 순서대로 할 일

| 번호 | 구현할 내용 |
|---|---|
| 01-01 | 클라이언트는 입력 데이터를 EchoRequest의 본문 필드에 담고 직렬화한 바이트를 패킷 본문으로 전송한다. |
| 01-02 | 서버는 요청 본문을 EchoRequest로 파싱한다. 파싱에 실패하면 InvalidPayload를 반환하고 성공 응답으로 처리하지 않는다. |
| 01-03 | 서버는 읽은 원문을 EchoResponse에 담아 직렬화한다. 응답 크기 초과와 직렬화 실패를 구분하여 기존 에러 규칙에 따라 처리한다. |
| 01-04 | 클라이언트는 응답의 요청 코드와 에러 코드를 확인한다. 성공한 Echo 응답만 EchoResponse로 파싱하고, 복원한 원문을 전송한 데이터와 비교한다. |
| 01-05 | 원문이 길면 여러 요청으로 나눈다. 각 EchoRequest의 직렬화 크기가 PacketHeader의 최대 본문 크기인 4092바이트 이하가 되도록 조각 크기를 결정한다. |
| 01-06 | 빈 입력, 널 바이트, 일반 텍스트가 아닌 바이트를 보존한다. 조각 응답을 수신 순서대로 결합하여 원문 전체를 복원한다. |
| 01-07 | 통합 테스트의 Echo, 바이너리 데이터, 연속 패킷, 종료 중 전송 경로를 같은 Protobuf 규격으로 변경한다. 고의로 잘못된 본문을 보내는 오류 검사는 별도로 구분한다. |

### 리뷰할 때 확인할 것

- 직렬화된 바이트 자체가 아니라 파싱한 원문이 일치한다.

- 모든 정상 Echo 전송 경로가 Protobuf를 사용하며, 크기 제한 때문에 일부 데이터가 빠지지 않는다.

- 확인 시나리오는 빈 입력, 바이너리 입력, 단일 패킷 경계 크기, 여러 패킷이 필요한 입력을 포함한다.

## 2단계 연결 세대 번호 적용

### 목표

재사용된 슬롯의 새 연결에 이전 연결의 작업이 적용되지 않게 한다.

### 열어볼 파일과 수정 범위

Define.hpp, ClientInfo.hpp, IOCPServer.hpp, PacketHandler.hpp, ZPDServer.hpp.

### 순서대로 할 일

| 번호 | 구현할 내용 |
|---|---|
| 02-01 | 연결 키는 슬롯 번호와 세대 번호를 포함한다. 사용자 ID와 연결 키를 서로 다른 식별자로 취급한다. |
| 02-02 | 연결이 성공할 때 해당 슬롯의 세대 번호를 증가시킨다. 연결에 실패한 소켓에 유효한 연결 키를 발급하지 않는다. |
| 02-03 | 연결, 수신, 송신 완료, 연결 종료 콜백은 연결 키 전체를 전달한다. 수신 시 받은 세대 정보를 송신 및 종료 요청까지 유지한다. |
| 02-04 | 송신과 연결 종료는 슬롯 범위, 연결 상태, 세대 일치를 검사한다. 세대 검사부터 실제 작업까지 동일한 연결 잠금을 유지한다. |
| 02-05 | 패킷 조립 버퍼는 연결 키별로 구분한다. 비교 가능한 연결 키와 map을 사용하며, 종료된 연결의 버퍼만 제거한다. |
| 02-06 | 연결 키를 읽는 작업은 세대 변경과 동시에 수행되지 않도록 보호한다. 다른 스레드에 키를 전달할 때는 값으로 보관한다. |
| 02-07 | 4단계에서 비동기 큐를 추가할 때 서버 정지 후 대기 작업을 모두 폐기하도록 한다. 재시작 이후 이전 작업이 새 연결로 전달되는 것을 허용하지 않는다. |

### 리뷰할 때 확인할 것

- 같은 슬롯의 연속된 두 연결은 서로 다른 키를 가진다.

- 이전 키로 송신 또는 연결 종료를 요청해도 새 연결에 영향이 없다.

- 이전 키의 버퍼 삭제가 새 키의 미완성 패킷을 제거하지 않는다.

## 3단계 패킷 조립과 처리 분리

### 목표

수신 버퍼를 보호하는 공유 mutex 밖에서 Protobuf 파싱과 응답 처리를 수행한다.

### 열어볼 파일과 수정 범위

PacketHandler.hpp. 아래는 4단계 이전의 학습 순서다. 현재 프로젝트에서는 이벤트 큐가 이 역할을 이어받으므로 임시 목록 구조로 되돌리지 않는다.

### 순서대로 할 일

| 번호 | 구현할 내용 |
|---|---|
| 03-01 | 완성된 요청을 임시 목록에 저장한다. 각 요청은 요청 코드, 에러 코드, 본문을 포함하며 수신 순서대로 목록에 추가한다. |
| 03-02 | 추출한 본문은 별도 메모리에 복사한다. 수신 버퍼를 가리키는 포인터나 참조를 임시 목록에 보관하지 않는다. |
| 03-03 | 잠금 안에서는 데이터 누적, 헤더 길이 검증, 완성된 요청 추출, 사용한 바이트 제거, 미완성 패킷 보관만 수행한다. |
| 03-04 | 잠금을 해제한 뒤 임시 목록의 요청을 순서대로 Dispatch에 전달한다. 잠금 안에서 Protobuf 파싱이나 응답 생성을 실행하지 않는다. |
| 03-05 | Dispatch는 요청 패킷 하나를 입력받고, 그 패킷에서 코드와 본문 길이를 확인한다. 본문 길이는 소유한 본문의 실제 크기를 사용한다. |
| 03-06 | 요청마다 응답을 직렬화하고 송신한다. 송신 실패 시 Handle은 기존처럼 실패를 반환한다. |
| 03-07 | Echo와 Ping 규격, 크기 제한, 잘못된 헤더 처리, 분할 및 연속 수신 동작을 유지한다. 같은 연결의 Handle 호출이 직렬화된다는 현재 전제를 유지한다. |

### 리뷰할 때 확인할 것

- Dispatch와 응답 직렬화가 공유 잠금 밖에서 실행된다.

- 수신 버퍼를 정리한 뒤에도 추출한 요청의 본문이 유효하다.

- 미완성 패킷은 보존되며 완성된 요청은 수신 순서대로 처리된다.

## 4단계 게임 명령 큐와 로직 스레드 추가

### 목표

네트워크 콜백과 게임 처리를 분리하고 게임 작업의 실행 순서를 한 곳에서 관리한다.

### 열어볼 파일과 수정 범위

게임 명령 및 큐 구성 요소 신규 추가. PacketHandler, ZPDServer와 서버 시작 및 종료 경로 수정.

### 순서대로 할 일

| 번호 | 구현할 내용 |
|---|---|
| 04-01 | 연결 생성, 패킷 처리 요청, 연결 종료를 구분하는 이벤트를 정의한다. 모든 이벤트는 연결 키와 처리에 필요한 데이터를 직접 소유한다. |
| 04-02 | 3단계에서 추출한 패킷을 게임 큐로 전달한다. IOCP 콜백은 게임 상태를 변경하지 않으며, 로직 스레드가 패킷 파싱과 Dispatch를 수행한다. |
| 04-03 | 로직 스레드 하나가 큐를 소비한다. 같은 연결에서는 연결 생성, 수신 요청, 연결 종료 순서가 유지되어야 한다. |
| 04-04 | 큐에는 유한한 용량을 두고 설정값을 문서화한다. 일반 요청이 가득 차면 해당 연결의 요청을 거절하고 종료한다. 종료 이벤트는 예약 용량 등으로 반드시 전달할 수 있게 한다. |
| 04-05 | 큐에 작업이 없으면 로직 스레드는 대기하고, 새 작업 또는 종료 신호가 오면 깨어난다. 큐 잠금을 잡은 채 게임 처리나 송신을 수행하지 않는다. |
| 04-06 | 작업 실행 시 현재 연결 키인지 확인한다. 만료된 연결의 명령은 상태 변경이나 새 연결로의 응답 없이 폐기한다. |
| 04-07 | 종료는 일반 요청 접수 중단, 로직 스레드 깨우기와 종료 대기, 네트워크 정지와 I/O 정리, 게임 상태 및 대기 이벤트 폐기 순으로 처리한다. 로직 스레드 종료 전에는 네트워크 연결 저장소를 해제하지 않는다. |
| 04-08 | 시작 도중 실패해도 생성한 스레드와 큐를 정리한다. 재시작은 큐와 게임 상태가 비워진 상태에서 시작하며, 작업 중 예외가 스레드 밖으로 전파되지 않게 한다. |

### 리뷰할 때 확인할 것

- IOCP 콜백의 반환 후에도 큐의 요청 데이터가 유효하다.

- 연결 이벤트 순서가 유지되며 큐 포화 시 종료 이벤트가 유실되지 않는다.

- 빈 큐와 대기 작업이 있는 경우 모두 종료가 끝나고 재시작 후 이전 작업이 실행되지 않는다.

## 5단계 플레이어 세션 관리

### 목표

연결된 사용자의 서버 내 상태와 소속 방을 관리한다.

### 열어볼 파일과 수정 범위

PlayerSession과 플레이어 관리자 신규 추가. 게임 이벤트 처리 및 개발용 입장 메시지 추가.

### 순서대로 할 일

| 번호 | 구현할 내용 |
|---|---|
| 05-01 | 플레이어 세션에 서버가 발급한 플레이어 ID, 현재 연결 키, 플레이어 상태, 선택적인 소속 방 ID를 저장한다. |
| 05-02 | 게임 로직 스레드만 플레이어 세션을 생성하거나 변경한다. 연결 키로 플레이어를 찾고 플레이어 ID로 현재 연결을 조회할 수 있게 한다. |
| 05-03 | 연결만 된 상태에서는 개발용 입장과 Ping 등 허용한 요청만 처리한다. 입장이 완료되면 Lobby 상태로 전환한다. |
| 05-04 | 개발용 입장은 서버가 임시 플레이어 ID를 발급하는 동작으로 한정한다. 실제 계정 인증이나 기존 사용자 신원 확인을 수행한 것으로 표시하지 않는다. |
| 05-05 | 같은 연결의 중복 입장은 오류로 응답하고 플레이어를 추가 생성하지 않는다. 입장 전 방 관련 요청도 오류로 응답한다. |
| 05-06 | 요청 발신자는 연결 키와 서버 세션 정보로 결정한다. 요청 본문의 플레이어 ID만으로 다른 플레이어의 상태를 변경하지 않는다. |
| 05-07 | 연결 종료 이벤트는 현재 세대가 일치하는 세션만 정리한다. 이미 정리된 세션의 중복 종료는 상태를 다시 변경하지 않는다. |

### 리뷰할 때 확인할 것

- 유효한 연결과 플레이어의 대응이 일관되며 중복 입장으로 세션이 늘어나지 않는다.

- 입장 전 방 요청이 거절되고 입장 이후에만 방 기능을 사용할 수 있다.

- 실제 인증이 없는 개발용 기능이라는 구분이 명확하다.

## 6단계 요청 응답 알림 규격 정의

**현재 미착수입니다. 아래 순서는 재개 요청 후에만 적용합니다.**

1. 기존 Echo·Ping·Enter의 요청/응답 코드와 대응 표를 먼저 정한다.
2. 서버와 클라이언트, raw 패킷 테스트 소스를 함께 새 코드로 전환한다. 클라이언트가 응답/알림 코드를 요청으로 보내면 거절한다.
3. 요청 식별자의 폭과 바이트 순서를 정하고 헤더 직렬화·파싱·크기 제한을 함께 바꾼다.
4. 방 생성·참가·퇴장 메시지와 참가자 알림을 정의한다. 방의 실제 생성·정원 처리는 7단계다.

### 목표

방 관련 통신을 서버와 클라이언트가 동일하게 해석할 수 있도록 규격을 확정한다.

### 열어볼 파일과 수정 범위

PacketCode.hpp, Packet.hpp, proto 스키마, PacketHandler와 클라이언트 패킷 처리 경로.

### 순서대로 할 일

| 번호 | 구현할 내용 |
|---|---|
| 06-01 | 개발용 입장, 방 생성, 방 입장, 방 퇴장에 대해 요청과 응답 메시지를 각각 정의한다. PlayerJoined와 PlayerLeft는 서버 알림으로 정의한다. |
| 06-02 | 요청, 응답, 알림은 서로 다른 메시지 코드로 구분한다. 메시지 코드와 Protobuf 본문 타입의 대응 목록을 문서화하고 중복 코드를 허용하지 않는다. |
| 06-03 | 패킷 헤더에 요청 식별자를 추가한다. 요청은 연결 안에서 미완료 요청과 겹치지 않는 0이 아닌 식별자를 사용하고, 응답은 같은 값을 반환한다. 알림은 0을 사용한다. |
| 06-04 | 전체 길이, 메시지 코드, 에러 코드, 요청 식별자의 바이트 폭과 바이트 순서를 명시한다. 헤더 크기가 바뀌면 최대 본문 크기와 모든 길이 검사를 함께 변경한다. |
| 06-05 | 개발용 입장 전 요청, 없는 방, 정원 초과, 이미 방에 속함, 방에 속하지 않음, 허용되지 않은 상태, 잘못된 본문을 구분하는 오류를 정의한다. 오류 응답 본문은 비운다. |
| 06-06 | 클라이언트가 응답 또는 알림 코드를 요청으로 보내면 거절한다. 파싱 실패와 상태 검증 실패가 성공 응답으로 전달되지 않게 한다. |
| 06-07 | 서버와 클라이언트를 같은 규격으로 전환한다. 이전 헤더와 새 헤더의 혼용을 지원하지 않는다. 배포된 필드 번호는 재사용하지 않고 삭제 시 예약한다. |

### 리뷰할 때 확인할 것

- 모든 메시지의 방향, 코드, 본문 타입, 오류와 요청 식별자 규칙이 정해져 있다.

- 클라이언트가 동시에 보낸 요청의 응답을 구분하고 알림을 별도로 처리할 수 있다.

- 헤더 변경 후 패킷 최대 크기와 분할 수신 처리가 일관된다.

## 7단계 방 생성 입장 퇴장 구현

### 목표

하나의 서버에서 여러 방과 참가자 소속을 일관되게 관리한다.

### 열어볼 파일과 수정 범위

GameSession과 방 관리자 신규 추가. 플레이어 세션과 방 명령 처리 수정.

### 순서대로 할 일

| 번호 | 구현할 내용 |
|---|---|
| 07-01 | 방에 서버가 발급한 방 ID, 정원, 참가자 목록, 상태를 저장한다. 초기 방 상태는 Waiting으로 두고, 존재하지 않는 방 ID는 유효한 방으로 취급하지 않는다. |
| 07-02 | 방 생성은 입장 완료 상태이고 다른 방에 속하지 않은 플레이어만 요청할 수 있다. 정원은 서버 설정 범위 안에서 검증하며 생성자를 자동 참가시킨다. |
| 07-03 | 방 입장은 방 존재, Waiting 상태, 남은 정원, 요청자의 현재 소속을 모두 검사한다. 다른 방에 속한 요청자는 자동 이동시키지 않고 오류로 응답한다. |
| 07-04 | 정원 확인과 참가자 추가는 동일한 게임 로직 처리 안에서 수행한다. 여러 입장 요청이 연속 처리되어도 정원을 초과하지 않아야 한다. |
| 07-05 | 입장 성공 시 방 참가자 목록과 플레이어의 방 ID를 함께 갱신한다. 실패 시 두 정보 모두 기존 상태를 유지한다. |
| 07-06 | 퇴장 성공 시 두 소속 정보를 함께 제거하고 플레이어를 Lobby로 되돌린다. 소속 방이 없는 명시적 퇴장 요청은 해당 오류로 응답한다. |
| 07-07 | 마지막 참가자가 나간 방은 제거한다. 방장 권한은 초기 범위에 포함하지 않으며 생성자의 퇴장이 다른 참가자를 강제로 내보내지 않게 한다. |

### 리뷰할 때 확인할 것

- 한 플레이어는 최대 하나의 방에 속한다.

- 정원 초과, 중복 입장, 없는 방 요청은 상태 변경 없이 거절된다.

- 모든 참가자의 소속 정보가 방 목록과 일치하고 빈 방이 남지 않는다.

## 8단계 참가자 알림 전송

### 목표

하나의 방 요청에 대한 응답과 다른 참가자에게 보낼 알림을 각각 전달한다.

### 열어볼 파일과 수정 범위

방 명령 처리, 서버 송신 경로, 응답 및 알림 메시지 생성 로직.

### 순서대로 할 일

| 번호 | 구현할 내용 |
|---|---|
| 08-01 | 상태 변경에 성공한 뒤 응답과 알림을 만든다. 실패한 요청으로 참가자 입장 또는 퇴장 알림을 만들지 않는다. |
| 08-02 | 입장자에게 방 ID, 정원, 현재 참가자 목록을 응답한다. 참가자 목록은 입장자 자신을 포함한 입장 완료 상태의 목록이다. |
| 08-03 | 기존 참가자에게 PlayerJoined를 보낸다. 입장자에게는 같은 입장 알림을 중복 전송하지 않는다. |
| 08-04 | 명시적 퇴장자에게 처리 결과를 응답한다. 남아 있는 참가자에게 PlayerLeft를 보내고, 퇴장자를 알림 수신 대상에서 제외한다. |
| 08-05 | 송신 대상은 해당 방의 참가자로 제한한다. 플레이어의 현재 연결 키를 사용하며 실제 송신 직전에 세대와 연결 상태를 확인한다. |
| 08-06 | 한 참가자의 송신 실패가 다른 참가자에 대한 송신을 중단하지 않게 한다. 실패한 연결은 종료 처리하고 9단계의 공통 정리 흐름으로 연결한다. |
| 08-07 | 같은 방에서 발생한 상태 변경 순서대로 각 연결의 송신 큐에 알림을 넣는다. 요청자에게 응답이 도착하기 전에 다른 참가자가 알림을 받을 수 있다는 점은 허용한다. |

### 리뷰할 때 확인할 것

- 입장자는 현재 방 상태를, 기존 참가자는 입장 알림을 받는다.

- 퇴장 후 남은 참가자에게만 퇴장 알림이 전달되며 다른 방에는 전달되지 않는다.

- 한 연결의 실패나 오래된 키가 다른 참가자의 알림 처리를 방해하지 않는다.

## 9단계 연결 종료와 방 정리 통합

### 목표

예기치 않은 연결 종료와 중복 이벤트에도 참가자 상태를 정확히 정리한다.

### 열어볼 파일과 수정 범위

연결 종료 이벤트 처리, 플레이어 관리자, 방 관리자, 공통 퇴장 처리.

### 순서대로 할 일

| 번호 | 구현할 내용 |
|---|---|
| 09-01 | 연결 종료를 게임 큐의 이벤트로 처리한다. 네트워크 콜백에서 방 참가자 목록이나 플레이어 상태를 직접 변경하지 않는다. |
| 09-02 | 명시적 퇴장과 연결 종료가 동일한 방 탈퇴 처리 기능을 사용하게 한다. 연결 종료 시에는 닫힌 연결에 퇴장 응답을 보내지 않는다. |
| 09-03 | 종료된 키와 플레이어의 현재 연결 키를 비교한다. 다른 세대의 종료 이벤트가 현재 플레이어 세션을 지우지 않게 한다. |
| 09-04 | 소속 방에서 참가자를 제거하고 남은 참가자에게 한 번만 퇴장 알림을 보낸다. 중복 종료나 이미 처리된 퇴장은 아무 변경 없이 종료한다. |
| 09-05 | 참가자가 제거된 뒤 빈 방을 삭제하고 플레이어 세션 및 조회 정보를 정리한다. 다음 요청에서 제거된 객체를 참조하지 않게 한다. |
| 09-06 | 송신 실패로 발생한 종료도 같은 흐름으로 처리한다. 종료된 연결의 대기 명령은 실행 시 확인하여 폐기한다. |
| 09-07 | 초기에는 연결 종료 즉시 참가자를 제거하고 재접속 복구를 제공하지 않는다. 서버 전체 종료 시에는 알림 전달 완료를 기다리지 않고 스레드 종료 후 모든 게임 상태를 정리한다. |

### 리뷰할 때 확인할 것

- 소켓 종료와 명시적 퇴장이 동일한 방 상태를 만든다.

- 중복 이벤트에 의해 참가자 수가 잘못 줄거나 알림이 중복 생성되지 않는다.

- 마지막 참가자 종료 후 빈 방과 플레이어 조회 정보가 남지 않는다.

## 10단계 대화형 클라이언트 방 기능 완성

### 목표

두 클라이언트에서 방 생성과 참가자 입장 및 퇴장을 직접 확인할 수 있게 한다.

### 열어볼 파일과 수정 범위

tests/echo_client.cpp와 tests/server_tests.cpp. 필요한 클라이언트 통신 보조 구성 요소.

### 순서대로 할 일

| 번호 | 구현할 내용 |
|---|---|
| 10-01 | 개발용 입장과 방 생성, 방 입장, 방 퇴장 명령을 제공한다. 잘못된 방 ID나 명령 인자는 사용자에게 알려주고 전송하지 않는다. |
| 10-02 | 패킷을 읽는 수신 루프는 연결당 하나만 둔다. 사용자 입력이 없어도 서버 응답과 알림을 계속 수신한다. |
| 10-03 | 응답은 요청 식별자로 대기 요청과 연결한다. 알림은 별도 처리하여 현재 방 참가자 표시를 갱신한다. |
| 10-04 | 입장 응답의 참가자 목록을 초기 상태로 사용하고 입장 및 퇴장 알림을 반영한다. 방을 나가면 로컬 참가자 목록을 비운다. |
| 10-05 | 연결 종료, 응답 파싱 실패, 알 수 없는 메시지, 서버 오류를 사용자에게 표시한다. 연결 종료 시 미완료 요청도 실패로 정리한다. |
| 10-06 | 종료 명령은 수신 대기를 해제하고 수신 스레드가 끝난 뒤 소켓 자원을 정리한다. 콘솔 입력 대기로 프로그램 종료가 무기한 막히지 않게 한다. |
| 10-07 | 통합 검증 항목에 두 클라이언트 입장, 정원 초과, 다른 방 격리, 중복 입장, 명시적 퇴장, 강제 연결 종료, 오래된 연결 키, 서버 종료와 재시작을 포함한다. |

### 리뷰할 때 확인할 것

- 두 클라이언트가 같은 방의 참가자 목록을 일관되게 표시한다.

- 입력 대기 중에도 상대의 입장과 퇴장 알림을 표시한다.

- 두 클라이언트 종료 후 방이 정리되고 서버와 클라이언트가 종료 대기에서 멈추지 않는다.

## 전체 완료 기준과 후속 확장

### 최종 확인 시나리오

1. 두 클라이언트가 접속하고 각각 개발용 입장을 완료한다.

2. 첫 번째 클라이언트가 방을 생성하고 반환된 방 ID를 확인한다.

3. 두 번째 클라이언트가 같은 방에 입장한다. 입장자는 전체 참가자 목록을 받고 기존 참가자는 입장 알림을 받는다.

4. 별도 방의 참가자가 이 방의 알림을 받지 않는지 확인한다.

5. 정원 초과와 중복 입장이 오류로 끝나고 기존 참가자 목록이 유지되는지 확인한다.

6. 한 참가자가 명시적으로 퇴장하거나 연결을 끊는다. 남은 참가자는 한 번의 퇴장 알림을 받는다.

7. 마지막 참가자가 나가면 방이 제거된다. 슬롯이 재사용된 뒤 이전 연결 키의 작업은 새 연결에 영향을 주지 않는다.

8. 서버를 종료하고 재시작한다. 이전 대기 명령과 방 상태가 새 실행으로 넘어가지 않는다.

### 진행 기록 갱신 방법

작업_진행_기록.md에 작업일, 수정 파일, 해당 요구사항 번호, 코드 리뷰 결과, 실행 여부, 남은 항목을 적는다. 실행하지 않았다면 미실행으로 표시한다. 다음 단계의 설명만 한 경우에는 미착수 상태를 유지한다.

### 후속 확장 범위

- 게임 진행: 준비 상태, 로딩 완료, 시작 조건, 종료 조건과 결과 처리.

- 게임 업데이트: 일정한 갱신 주기, 서버 기준 이동 및 전투 판정, 입력 순서 관리.

- 사용자 복구: 실제 인증, 재접속 자격 확인, 복구 유예 시간과 재접속 시 상태 동기화.

- 처리량 확대: 방을 여러 게임 워커에 배정하되 같은 방의 상태 변경은 한 번에 한 워커만 수행.

- 운영 기능: 데이터 저장, 큐 및 지연 관측, 서버 간 방 배정과 버전 호환 정책.
